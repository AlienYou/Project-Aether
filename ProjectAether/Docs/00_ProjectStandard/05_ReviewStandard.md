## 1. 文档目的

本文档定义 Project Aether 的统一评审规范，适用于架构、设计、代码、测试、性能、资源、配置、网络、发布和文档评审。

本规范的目标是：

- 在问题进入主分支或正式版本前发现风险。
- 保证实现符合 Project Aether 的架构和编码规范。
- 保证重要技术决策经过明确讨论和记录。
- 保证评审结论可追踪、可执行、可复查。
- 降低多人协作中的理解偏差和返工成本。
- 防止 AI 生成代码绕过项目既有基线。
- 建立适用于长期商业项目的质量门禁。

---

## 2. 适用范围

本规范适用于：

- Project Standard 评审。
- Architecture 评审。
- Design 评审。
- RFC 评审。
- Code Review。
- Test Review。
- Performance Review。
- Memory Review。
- Network Review。
- Security Review。
- Asset Review。
- Build Review。
- Release Review。
- Documentation Review。
- AI 生成内容评审。

所有进入共享分支、主分支或正式版本的重要修改都必须经过相应评审。

---

## 3. 核心原则

### 3.1 Review Is a Quality Gate

评审不是形式流程。

评审必须能够阻止以下内容进入后续阶段：

- 与架构冲突的实现。
- 生命周期不完整的系统。
- 明显无法编译的代码。
- 缺少测试的高风险修改。
- 未说明兼容性的公共 API 变化。
- 未说明资源所有权的加载逻辑。
- 未说明网络权威的同步逻辑。
- 未说明性能影响的热点路径修改。
- 未同步文档的架构变更。
- 未经确认的 AI 重构。

---

### 3.2 Review the Change, Not the Person

评审针对：

- 设计。
- 代码。
- 风险。
- 行为。
- 测试。
- 文档。

禁止针对个人能力、身份或表达方式进行评价。

正确：

```text
该方法同时负责缓存查询、加载和释放，建议拆分职责。
```

禁止：

```text
你这个写法太差了。
```

---

### 3.3 Evidence Over Preference

评审意见应基于：

- 项目规范。
- 架构文档。
- 当前代码。
- 测试结果。
- 性能数据。
- Unity 行为。
- 第三方官方文档。
- 可复现问题。

仅属于个人风格偏好的意见，不得作为阻塞项。

---

### 3.4 Blocking Issues Must Be Explicit

阻塞问题必须明确说明：

- 问题位置。
- 风险。
- 为什么必须修改。
- 建议修复方向。
- 验收条件。

禁止只写：

```text
这里不行。
```

---

### 3.5 Review Must Be Traceable

重要评审必须保留：

- 评审对象。
- 评审版本。
- 评审人员。
- 评审时间。
- 问题列表。
- 修改结果。
- 最终结论。

---

### 3.6 Review Scope Must Be Controlled

单次评审范围必须明确。

禁止在一个 PR 中同时评审大量无关变更。

当修改过大时，应先拆分：

- 架构。
- 基础接口。
- 核心实现。
- 测试。
- 文档。
- 调用方迁移。

---

### 3.7 The Author Owns the Change

评审人负责发现问题和提供建议。

作者负责：

- 理解意见。
- 修改代码。
- 补充说明。
- 补充测试。
- 更新文档。
- 说明未采纳原因。

评审人不应默认替作者完成所有修改。

---

## 4. 评审类型

Project Aether 使用以下评审类型：

| 类型 | 主要目的 |
|---|---|
| Standard Review | 评审项目规范 |
| Architecture Review | 评审系统职责、边界和依赖 |
| Design Review | 评审详细方案和实现路径 |
| RFC Review | 评审重大技术变更 |
| Code Review | 评审代码质量和实现正确性 |
| Test Review | 评审测试覆盖与验收结果 |
| Performance Review | 评审性能风险和数据 |
| Memory Review | 评审生命周期和泄漏风险 |
| Network Review | 评审权威、同步、协议和安全 |
| Asset Review | 评审资源规范和运行成本 |
| Build Review | 评审构建流程和平台配置 |
| Release Review | 评审版本发布条件 |
| Documentation Review | 评审文档完整性和一致性 |
| AI Output Review | 评审 AI 生成内容是否符合项目基线 |

## 5. 评审等级

### 5.1 Lightweight Review

适用于：

- 小型 Bug 修复。
- 小范围文档修改。
- 不改变行为的简单重构。
- 低风险工具修改。

要求：

- 至少一名评审人。
- 基础测试通过。
- 不影响公共 API。
- 不影响架构和数据格式。

---

### 5.2 Standard Review

适用于：

- 普通功能。
- 模块内部改动。
- 新增公开但局部的 API。
- 中等风险性能修改。
- 常规资源或配置流程修改。

要求：

- 至少一名熟悉模块的评审人。
- 必要时增加跨模块评审人。
- 相关测试通过。
- 文档同步。

---

### 5.3 Critical Review

适用于：

- 核心框架修改。
- 公共接口破坏性变化。
- 网络协议变化。
- 存档格式变化。
- 资源生命周期变化。
- 初始化顺序变化。
- 核心性能路径变化。
- 发布阻塞问题。
- 安全相关修改。

要求：

- 至少两名评审人。
- 项目负责人或架构负责人参与。
- 必须有设计或 RFC。
- 必须有测试记录。
- 必须明确回滚方案。
- 必须完成复审。

---

## 6. 问题等级

### 6.1 Blocker

不修复不得合入。

典型情况：

- 无法编译。
- 明确崩溃。
- 数据损坏。
- 资源泄漏。
- 线程安全问题。
- 网络作弊风险。
- 破坏核心架构。
- 破坏公共接口且无迁移方案。
- 严重性能回退。
- 敏感信息泄露。
- 测试无法通过。

标记：

```text
[Blocker]
```

---

### 6.2 Major

高风险问题，原则上必须修改。

典型情况：

- 职责明显混乱。
- 生命周期不完整。
- 错误处理不足。
- 重要边界未覆盖。
- 公共 API 容易误用。
- 存在明显 GC 风险。
- 文档与实现不一致。
- 缺少关键测试。

标记：

```text
[Major]
```

---

### 6.3 Minor

不影响合入，但应尽量处理。

典型情况：

- 命名不够准确。
- 局部可读性问题。
- 可维护性改进。
- 注释不足。
- 非关键测试缺失。
- 轻微重复代码。

标记：

```text
[Minor]
```

---

### 6.4 Suggestion

可选改进，不应阻塞合入。

典型情况：

- 替代实现建议。
- 未来扩展方向。
- 非必要重构。
- 个人偏好但有合理依据。

标记：

```text
[Suggestion]
```

---

### 6.5 Question

需要作者澄清，不一定代表问题。

标记：

```text
[Question]
```

---

### 6.6 Praise

用于标记值得保留的优秀设计。

标记：

```text
[Praise]
```

适当的正向反馈有助于团队建立可复用的优秀模式。

## 7. 评审角色

### 7.1 Author

作者负责：

- 提交完整内容。
- 自检。
- 提供背景。
- 说明风险。
- 提供测试结果。
- 回应评审意见。
- 完成修改。
- 请求复审。

---

### 7.2 Reviewer

评审人负责：

- 理解修改目标。
- 检查规范和架构一致性。
- 发现风险。
- 提供可执行意见。
- 区分阻塞问题和建议。
- 复查修改结果。
- 给出最终结论。

---

### 7.3 Module Owner

模块负责人负责：

- 确认模块边界。
- 确认 API 设计。
- 确认生命周期。
- 确认兼容性。
- 处理模块内争议。

---

### 7.4 Architecture Owner

架构负责人负责：

- 评审跨模块依赖。
- 评审核心架构变化。
- 评审 RFC。
- 确认系统级一致性。
- 处理重大技术分歧。

---

### 7.5 Project Lead

项目负责人负责：

- 确认优先级。
- 确认风险接受。
- 确认发布门禁。
- 在技术和进度冲突时作出最终决策。

---

## 8. 评审前置条件

提交评审前，作者必须确认：

- [ ] 修改目标明确。
- [ ] 代码已经完成。
- [ ] 当前分支已同步。
- [ ] 项目可以编译。
- [ ] 相关测试已经执行。
- [ ] 调试代码已清理。
- [ ] 文档已经同步。
- [ ] Diff 中没有无关修改。
- [ ] Commit 信息符合规范。
- [ ] PR 描述完整。
- [ ] 已知风险已说明。
- [ ] 回滚方案已说明。
- [ ] 相关 RFC、Design、Test 已关联。

不满足前置条件的评审可以直接退回。

## 9. 评审流程

统一流程：

```text
Prepare Change
  ↓
Author Self Review
  ↓
Create Pull Request
  ↓
Assign Reviewers
  ↓
Review
  ↓
Resolve Findings
  ↓
Re-Review
  ↓
Approve
  ↓
Merge
  ↓
Post-Merge Verification
```

## 10. Author Self Review

作者在请求评审前，必须先自行检查完整 Diff。

推荐执行：

```bash
git status
git diff
git diff --staged
```

作者自检重点：

- 是否存在意外文件。
- 是否存在临时日志。
- 是否存在注释代码。
- 是否存在错误命名。
- 是否存在重复逻辑。
- 是否遗漏测试。
- 是否遗漏文档。
- 是否影响其他模块。
- 是否引入破坏性变化。

---

## 11. Pull Request 描述

评审请求必须包含：

```markdown
## Summary

本次修改解决的问题。

## Background

修改背景。

## Changes

主要修改内容。

## Architecture Impact

是否影响架构、模块边界、生命周期或公共 API。

## Test

测试环境、步骤和结果。

## Performance

性能影响和数据。

## Risk

已知风险。

## Rollback

回滚方式。

## Related Documents

相关 Architecture、Design、RFC、Test、Decision Log。
```

不适用的章节应写：

```text
Not applicable.
```

不要直接删除，使评审人无法判断是否被遗漏。

---

## 12. 评审响应时效

团队可根据实际规模调整。

推荐：

- Lightweight Review：一个工作日内首次响应。
- Standard Review：两个工作日内首次响应。
- Critical Review：安排正式评审会议。

评审人无法及时处理时，应尽早说明并转交其他合适人员。

---

## 13. 评审意见格式

推荐格式：

```text
[Major] ResourceManager owns both cache eviction and scene lifetime decisions.

Risk:
This couples the resource layer to gameplay scene rules.

Suggestion:
Move scene lifetime policy into a higher-level resource scope service.

Acceptance:
ResourceManager only manages resource handles and cache state.
```

评审意见应包含：

- 等级。
- 位置。
- 问题。
- 风险。
- 建议。
- 验收条件。

---

## 14. 评审意见处理

作者必须对每条意见做出以下之一：

- Fixed。
- Accepted。
- Rejected with reason。
- Deferred with task。
- Need discussion。

禁止：

- 无说明地 Resolve。
- 删除评论。
- 修改后不通知评审人。
- 将 Blocker 转为后续任务后直接合入，除非负责人明确接受风险。

---

## 15. 技术分歧处理

发生技术分歧时：

1. 明确双方目标。
2. 明确约束。
3. 引用项目规范。
4. 提供数据或可复现验证。
5. 比较方案。
6. 记录结论。
7. 必要时创建 RFC 或 Decision Log。

禁止通过职位、情绪或反复争论代替证据。

---

## 16. Architecture Review

Architecture Review 重点检查：

- 系统目标是否明确。
- 模块职责是否单一。
- 模块边界是否清晰。
- 依赖方向是否正确。
- 是否存在循环依赖。
- 生命周期是否完整。
- 数据流是否清晰。
- 公共接口是否稳定。
- 扩展点是否合理。
- 错误策略是否明确。
- 性能约束是否说明。
- 是否支持测试。
- 是否有迁移和回滚方案。

## 18. Design Review

Design Review 重点检查：

- 问题定义是否准确。
- 是否存在更简单方案。
- 是否与 Architecture 一致。
- 数据结构是否合理。
- 状态机是否完整。
- 异常路径是否覆盖。
- 是否考虑边界条件。
- 是否考虑性能。
- 是否考虑测试。
- 是否考虑未来扩展。
- 是否过度设计。

## 20. RFC Review

RFC Review 必须确认：

- 变更是否真的需要 RFC。
- 影响范围是否完整。
- 方案是否兼容。
- 是否需要数据迁移。
- 是否影响存档。
- 是否影响协议。
- 是否影响第三方库。
- 是否可以逐步发布。
- 是否可以回滚。
- 是否有替代方案。
- 是否记录最终决策。

---

## 21. Code Review

Code Review 的目标不是寻找格式问题，而是确认实现：

- 正确。
- 清晰。
- 安全。
- 可维护。
- 可测试。
- 符合架构。
- 符合性能要求。

格式问题应尽量由自动化工具处理。

---

## 22. Code Review 顺序

推荐评审顺序：

1. 阅读 PR 描述。
2. 阅读相关 Architecture 或 Design。
3. 查看整体 Diff。
4. 检查公共 API。
5. 检查生命周期。
6. 检查状态与数据流。
7. 检查错误处理。
8. 检查异步和线程。
9. 检查性能。
10. 检查测试。
11. 检查文档。
12. 给出结论。

不要从单个变量命名开始，忽略整体设计。

## 23. Code Review Checklist

### 23.1 Architecture

- [ ] 实现符合 Architecture。
- [ ] 模块职责没有扩散。
- [ ] 依赖方向正确。
- [ ] 没有隐藏全局依赖。
- [ ] 没有新增循环依赖。
- [ ] 公共接口变化已评审。

### 23.2 Correctness

- [ ] 正常路径正确。
- [ ] 错误路径正确。
- [ ] 边界条件正确。
- [ ] 空值处理正确。
- [ ] 重复调用安全。
- [ ] 状态转换合法。
- [ ] 数据一致性正确。
- [ ] 并发访问安全。

### 23.3 Readability

- [ ] 命名准确。
- [ ] 方法职责单一。
- [ ] 控制流清晰。
- [ ] 嵌套层级合理。
- [ ] 注释说明原因。
- [ ] 没有无意义抽象。
- [ ] 没有重复逻辑。

### 23.4 Lifecycle

- [ ] 创建流程明确。
- [ ] 初始化流程明确。
- [ ] 运行流程明确。
- [ ] Shutdown 流程明确。
- [ ] Dispose 流程明确。
- [ ] 事件订阅和取消成对。
- [ ] 资源 Retain 和 Release 成对。
- [ ] CancellationToken 正确取消。
- [ ] 静态状态正确清理。

### 23.5 Async

- [ ] 异步方法使用 Async 后缀。
- [ ] 长生命周期任务支持取消。
- [ ] 没有无必要 async void。
- [ ] fire-and-forget 处理异常。
- [ ] 超时策略明确。
- [ ] 并行任务失败策略明确。
- [ ] Unity API 仅在主线程使用。

### 23.6 Unity

- [ ] MonoBehaviour 职责轻量。
- [ ] 没有每帧查找对象。
- [ ] 没有无意义 Update。
- [ ] FixedUpdate 使用正确。
- [ ] Inspector 字段正确。
- [ ] 序列化兼容性已考虑。
- [ ] Editor 代码与 Runtime 隔离。
- [ ] Prefab 和 Scene 引用稳定。

### 23.7 Performance

- [ ] 热点路径无明显 GC。
- [ ] 没有无意义 LINQ。
- [ ] 没有高频字符串拼接。
- [ ] 集合选择合理。
- [ ] 集合容量合理。
- [ ] 缓存有失效策略。
- [ ] 对象池使用合理。
- [ ] 性能优化有数据支持。

## 46. 评审自动化

可自动化检查：

- 代码格式。
- 编译。
- 单元测试。
- 静态分析。
- Assembly 循环依赖。
- 资源命名。
- Meta 文件完整性。
- 敏感信息扫描。
- 文件大小。
- 文档链接。
- Commit 格式。
- PR 模板。

自动化不能替代架构和逻辑评审。

---

## 47. 评审质量检查

评审人应避免：

- 只看格式。
- 只看局部代码。
- 忽略 PR 目标。
- 将个人偏好标记为 Blocker。
- 给出无法执行的意见。
- 对同类问题标准不一致。
- 评审自己不了解的关键领域却不给出限制说明。

---

## 48. 过大 PR

出现以下情况应考虑拆分：

- Diff 超过合理阅读范围。
- 同时修改多个独立模块。
- 同时包含重构和新功能。
- 同时修改大量资源和代码。
- 评审人无法在一次评审中建立完整心智模型。

拆分原则：

```text
Architecture
  ↓
API
  ↓
Core Implementation
  ↓
Integration
  ↓
Tests
  ↓
Documentation
```

---

## 49. 紧急修复评审

Hotfix 仍必须评审。

最低要求：

- 至少一名合适评审人。
- 明确问题原因。
- 明确影响范围。
- 有回归测试。
- 有回滚方案。
- 发布后补充完整 Review 记录。

紧急不代表可以跳过质量门禁。

---

## 50. 复审

以下情况必须复审：

- Blocker 已修改。
- Major 已修改。
- 公共 API 再次变化。
- 解决冲突后逻辑发生变化。
- 作者新增了较大修改。
- 测试方案变化。
- 性能实现变化。
- 合并前进行了复杂 Rebase。

---

## 51. Post-Merge Verification

合入后应根据风险执行：

- Develop 编译。
- 自动化测试。
- 关键功能冒烟测试。
- 场景加载验证。
- Addressables 验证。
- 网络连接验证。
- 构建验证。

发现问题后应立即：

- 停止继续合入相关修改。
- 创建 Fix 或 Revert。
- 通知相关成员。
- 记录原因。

---

## 52. Review Metrics

团队可以记录：

- 首次响应时间。
- Review 完成时间。
- Blocker 数量。
- Major 数量。
- 合入后缺陷数量。
- Revert 数量。
- PR 大小。
- 测试覆盖变化。

指标用于改进流程，不用于简单评价个人绩效。

## 53. 常见错误

### 53.1 只评审风格

忽略架构、生命周期和正确性。

---

### 53.2 所有意见都设为阻塞

导致评审效率低下。

---

### 53.3 大型修改没有 Design

评审人只能从代码猜测意图。

---

### 53.4 作者只处理表面问题

没有理解风险，导致同类问题反复出现。

---

### 53.5 评审通过后继续大量修改

使原审批失效。

---

### 53.6 文档和测试被视为可选

导致长期维护困难。

## 55. 验收标准

本规范执行后，应达到：

- 重要修改在合入前经过适当评审。
- Blocker 和 Major 风险得到明确处理。
- 评审意见可执行、可追踪。
- 架构、代码、测试和文档保持一致。
- 大型修改有 Design 或 RFC 支撑。
- 发布版本经过正式门禁。
- AI 生成代码不会未经人工理解直接进入项目。
- 评审过程能够减少缺陷，而不是只增加流程成本。
- 团队可以通过 Review 记录恢复关键决策上下文。
